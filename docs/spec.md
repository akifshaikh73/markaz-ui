## 1. Product overview

**Product:** a web app ("Chicago Visitations") used by masjid volunteers to plan and record door-to-door household visits for each masjid, split by unit (a masjid's sub-area of responsibility). **[Doc / Inferred]**

**Users and roles** (source of truth for access: `src/App.js`):

| Role | Sign-in | Access |
|---|---|---|
| `MasjidUser` | Masjid PIN, or knowing the masjid slug (`/:masjidSlug`) | One masjid's listings: view, search, add/edit addresses, record visits, routes |
| `MasjidAdmin` | Email + PIN (`/user-login`), bcrypt-checked by the API | `MasjidUser` access for each assigned masjid, plus Map View, Excel export, latitude/longitude display |
| `MarkazAdmin` | Shared password (`REACT_APP_ADMIN_PASSWORD`) at `/admin-login` | All masjids, plus the Markaz Admin dashboard (masjids, users) |

**Deployment:** React 18 single-page app (Create React App, react-router v6) built as a Render static site; talks to a separate REST API (`REACT_APP_API_URL`, e.g. `https://visitation-api.onrender.com`) backed by MongoDB. The UI never hardcodes API hosts.

**Sources:** `src/App.js`, `AGENTS.md`, `CLAUDE.md`, `render.yaml`, `docs/functional-manual.md`.

## 3. Data model (listing)

The central record is a **listing** (one household) in the API's `listings` collection. Fields relevant to this spec:

| Field | Type | Notes |
|---|---|---|
| `_id` | string | Generated by the API from a sequence |
| `firstName`, `lastName` | string | Required on create |
| `address1` | string | Street + number; required, cannot be emptied once set |
| `address2` | string | Apt / suite / unit; `''` clears |
| `city` | string | |
| `state` | string | Two letters, stored upper-case |
| `zipcode` | **number** | Stored as an integer (`'60614'` → `60614`, empty → `0`; ZIP+4 keeps the first five digits' numeric value) |
| `masjidId`, `unitId` | integer | |
| `latitude`, `longitude` | number | `0` / `0` means **no location** (the API default on create) |
| `inactive` | boolean | Invalid / moved households are marked inactive |
| `listingSource` | string | The UI sends `'render-app'` on create |
| `visitHistory[]` | array | `{ response, comments, createdDate }` |
| `students[]`, `isStudent` | array / boolean | Student data |
| `version` | number | Incremented by the API on every update |

**Has-location rule (used everywhere):** a listing *has a location* when `latitude` and `longitude` are both truthy. Map View, Route View and the address-detail Route button all use this rule, so `0`/`0` and missing values are treated alike.

**Sources:** `AGENTS.md` (data shape), `visitation_api.js` (`POST /addressList`, `PUT /addressList/:id`), `src/Components/AddressDetail.js`.

## 5. Adding an address

### 5.1 Form

`AddAddress` (`src/Components/AddAddress.js`) is the "Add New Address" form on Full Listings and Visitations.

- **ADDR-1** The form shall offer: Masjid ID (read-only), Unit (choice from the masjid's units), First Name\*, Last Name\*, Address Line 1\*, Address Line 2, City, State (2 chars), Zip (≤10 chars), Phone Number, and an optional visit log (Response, Comment, Date).
- **ADDR-2** Unit shall default to the unit being viewed if it is one of the masjid's units, otherwise to the first unit; if units are still loading the form shall fill the unit in when they arrive, so a `null` unit is never submitted.
- **ADDR-3** Submitting without first name, last name or Address Line 1 shall show "First name, last name and address are required."; submitting without a valid unit shall show "Please select a unit."; neither shall call the API.
- **ADDR-4** The create request body shall contain trimmed `firstName`, `lastName`, `address1`; `address2`, `city`, `state`, `zipcode`, `phoneNumber` only when non-empty; `masjidId` and `unitId` as integers; `listingSource: 'render-app'`.
- **ADDR-5** If a Response or a Comment is entered, the body shall also contain `visitedDate`, `latestResponse` and `comments`. Response choices: Met, No Response, Left Message, Moved, Invalid, Do Not Disturb, Duplicate, Rented.
- **ADDR-6** On success the form shall show "Address Created" with the new ID, an **Add Another** button (which clears every field and resets the date to today) and **Close**, and shall call `onCreated(id)`; the list screen then shows the new listing at the top with a NEW badge **[Doc]**. On failure it shall show the error message and stay editable.
- **ADDR-7** While a request is in flight the submit button shall be disabled.

### 5.2 Duplicate check **[Doc, summarized]**

While Address Line 1/2 are typed (≈0.5 s debounce, needs a house number plus ≥2 letters of the street), the form lists existing listings in the same masjid — including inactive ones — at the same address ("This address already exists") or in the same building ("Other units at this address"). It never blocks saving. A match offers **Open listing**, or **Activate & open** for an inactive one. Details: `docs/functional-manual-user.md` §5; code: `src/hooks/useDuplicateAddressCheck.js`, `src/addressDuplicates.js`, `src/Components/DuplicateAddressWarning.js`. An `allowUpdateExisting` prop (default off) enables "Update this listing"/"Activate & save"; it is not used in production **[Open]**.

Detailed in §6 (service) and requirements `LOC-1`…`LOC-9` below.

### 5.4 Coordinates on create

### 5.6 `PUT /addressList/:id` (address and location fields)

- **API-1** Values shall be trimmed; only fields that differ from the stored value are written; `version` shall increase by one per update.
- **API-2** `address1`, if sent, shall be non-empty; `state` shall be empty or two letters (stored upper-case); `zipcode` shall be empty, five digits or ZIP+4 (stored as a number).
- **API-3** `latitude` and `longitude`, if either is sent, shall both be sent as numbers with latitude in −90…90 and longitude in −180…180; otherwise the API shall answer `400`. `0`/`0` is valid and clears the location.
- **API-4** The API shall not geocode; clients send coordinates.
- **API-5** The response is the Mongo update result; `modifiedCount: 0` means nothing changed. Clients treat `modifiedCount: 0` after sending address or coordinate fields as "the API does not support this yet" (see `LOC-18`).

**Sources:** `src/Components/AddAddress.js`, `visitation_api.js:283-395`, `visitation_api/docs/API.md`, `openapi.yaml`.

## 6. External services

The UI calls these third-party services **directly from the browser**; the Visitation API is not a proxy for any of them.

| # | Service | Endpoint | Used for | Files |
|---|---|---|---|---|
| E1 | **Mapbox Geocoding API v6** (forward) | `https://api.mapbox.com/search/geocode/v6/forward` | Street suggestions while typing on Add Address | `src/mapbox.js`, `AddressAutocompleteInput.js` |
| E2 | **OpenStreetMap Nominatim** (search) | `https://nominatim.openstreetmap.org/search` | (a) Turning a listing's address (or a city/zip) into latitude/longitude — `src/geocode.js`; (b) geocoding the masjid's own address for Route View's start point (not saved) — `RouteView.js`; (c) **address suggestions while typing** in the Markaz Admin masjid editor — `MasjidDetail.js` (see §6.2) | `src/geocode.js`, `RouteView.js`, `MasjidDetail.js` |
| E3 | Nominatim (reverse) | `https://nominatim.openstreetmap.org/reverse` | Masjid editor, "use current location" button: fills the address fields from the device's GPS position | `MasjidDetail.js` |
| E4 | **OSRM public demo router** | `https://router.project-osrm.org/route/v1/driving/…` | Driving route (distance, time, polyline) in Route View | `RouteView.js` |
| E5 | **OpenStreetMap raster tiles** | `https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png` | Map background in Map View, Route View, pin picker | `MapView.js`, `RouteView.js`, `PinPicker.js` |

### 6.1 Mapbox (E1)

- **Credential:** `REACT_APP_MAPBOX_TOKEN`, a **public** token (`pk.…`). It is compiled into the JavaScript bundle and is therefore visible to anyone, so it shall be URL-restricted in the Mapbox dashboard (localhost dev URL and the deployed URL). Never use a secret (`sk.`) token. Set it in `.env.local` for development and in the Render static site's environment for production; it is read at build/start time, so changing it needs a restart or redeploy.
- **Request:** `GET …/forward` with `q` (the text typed), `access_token`, `autocomplete=true`, `types=address`, `country=us`, `limit=5`, and `proximity=<lng>,<lat>` when the browser location is known (note the order: longitude first).
- **Response fields used:** per feature — `id` (fallback `properties.mapbox_id`), `properties.full_address` (fallback `properties.name`) as the label; `properties.context.address.name` (fallback `properties.name`) → Address Line 1; `context.place.name` → city; `context.region.region_code` → state; `context.postcode.name` → zip. Mapbox does not return apartment/unit numbers, so Address Line 2 is never filled from it.
- **Mode:** the standard ("temporary") geocoding mode, i.e. `permanent=true` is **not** sent. See §10 item 1 for the storage-terms question this raises.
- **Cost/limits:** one request per debounced keystroke burst. Check Mapbox's current pricing and free tier before changing usage **[Open]**.
- **Attribution:** the dropdown footer reads "Search by Mapbox".
- **Disabled state:** without a token the feature is off and the field behaves as a plain text input (no errors).

### 6.2 Nominatim (E2, E3)

- **Request (search):** `GET …/search?format=json&limit=1&countrycodes=us&q=<parts joined by ", ">` with header `Accept-Language: en`. Only the first hit is used; `lat`/`lon` strings are parsed to numbers and must both be finite.
- **Timeout:** 5 seconds, then the request is aborted. Any failure (network, non-2xx, non-array body, no hit) yields "no location" — never an exception.
- **Public-server policy the app must respect** (OpenStreetMap Foundation usage policy; re-check before relying on it): at most **one request per second**; **no search-as-you-type** (this is why the listing form's suggestions use Mapbox, and `src/geocode.js` is only called once per user action); the application must be identifiable (browsers cannot set `User-Agent`; the automatic `Referer` header is relied on); results should be cached; results are © OpenStreetMap contributors (ODbL) and shall be attributed. Storing the results is permitted under the license.
- **Attribution in the UI:** "Map location lookup © OpenStreetMap contributors" under the Add Address form; map tiles carry the standard OSM attribution.
- **Existing behavior that conflicts with that policy:** the Markaz Admin masjid editor (`MasjidDetail.js`) calls Nominatim search as the admin types — after a 400 ms pause, from 4 characters, `limit=5`, `addressdetails=1` — and offers the results as suggestions that fill address, city, state and zip. That is search-as-you-type on the public server (§10 item 12). It is a low-traffic admin screen, but it is the one place the app does not follow the policy above.
- **Not implemented:** client-side caching and throttling (§10 item 2).

### 6.3 OSRM and tiles (E4, E5)

Route View sends the stops' `lng,lat` pairs (masjid first) to the public OSRM demo server (`overview=full&geometries=geojson`) and shows `distance` converted from metres to miles and `duration` from seconds to whole minutes. The demo server and the volunteer-run OSM tile servers are best-effort services with no uptime guarantee and fair-use limits **[Open]**.

**Sources:** `src/mapbox.js`, `src/geocode.js`, `src/Components/RouteView.js:168,325`, `src/Components/MasjidDetail.js:53,84`, `src/Components/PinPicker.js`, `AGENTS.md`.

## 7. Map locations (requirements)

### 7.1 Suggestions while typing (Add Address, Address Line 1)

- **LOC-1** When `REACT_APP_MAPBOX_TOKEN` is set and at least 3 non-blank characters are typed, the form shall request suggestions after a 250 ms pause; each new request shall cancel the previous one; fewer than 3 characters shall close the list.
- **LOC-2** The browser's location shall be requested once, the first time the field gains focus, and used as the Mapbox `proximity` when granted (cache ≤10 min, 5 s timeout). Denial or absence shall not affect suggestions.
- **LOC-3** Suggestions shall be limited to US street addresses (E1 request above) and display the full address text.
- **LOC-4** The list shall support mouse selection (selection must work before the input loses focus), ArrowUp/ArrowDown to move, Enter to choose the highlighted item, Escape to close; it shall close when the field loses focus.
- **LOC-5** Choosing a suggestion shall set Address Line 1, City, State and Zip from it, replacing what was there.
- **LOC-6** Address Line 2 shall be set from the suggestion only if the suggestion has one **and** the field is empty; a value the user typed shall never be overwritten (Mapbox currently never supplies one).
- **LOC-7** A failed suggestion request shall show nothing and shall not block typing.
- **LOC-8** The user may ignore suggestions and type the whole address; nothing is required to be picked.
- **LOC-9** The dropdown shall show the "Search by Mapbox" attribution.

### 7.2 Coordinates when an address is created

- **LOC-10** On **Add Address**, after validation passes and before the create request, the form shall look up coordinates for the entered address (E2), using the address as it is at that moment (not what a suggestion originally returned).
- **LOC-11** The lookup shall run only when Address Line 1 is present **and** (city and state are present **or** zip is present). Otherwise it is skipped, because a street and number alone match towns across the whole US.
- **LOC-12** If coordinates are found they shall be sent as `latitude` and `longitude` in the create request. If not found, failed or timed out, the address shall still be created without them (the API then stores `0`/`0`). A geocoding problem shall never prevent adding an address.
- **LOC-13** Saving shall wait for the lookup (up to 5 s); the submit button stays disabled meanwhile.

### 7.3 Locate & route (address detail)

- **LOC-14** When a listing has no location (see §3), the address detail screen shall show **📍 Locate & route** in place of **🗺 Route**; with a location the Route button opens `/route` with this listing, as before.
- **LOC-15** Choosing **Locate & route** shall: look the address up (E2, same preconditions as `LOC-11`); if found, `PUT` `{ latitude, longitude }` to the listing, update the screen and local cache, then open `/route` with the listing including the new position. The button shows "Locating…" and is disabled meanwhile.
- **LOC-16** If the address is not found (or lacks city/state/zip), the screen shall show: "We couldn't find this address on the map. Check the street, city and zip, or place it on the map yourself." with **Fix address** (opens the address editor) and **Place on map**. No request is sent to the API and the route does not open.
- **LOC-17** **Place on map** shall show a map (pin picker) centred on the listing's city/zip when that can be looked up (zoom 16), otherwise on the centre of the US (zoom 4). Tapping the map places a pin; the pin can be dragged. **Save location** is disabled until a pin exists and while saving. Saving `PUT`s `{ latitude, longitude }`, closes the picker, and the button becomes **🗺 Route**. **Cancel** closes the picker without saving. The picker is loaded on demand (lazy) so the map library is not in the main bundle.
- **LOC-18** If the API answers `modifiedCount: 0` to a coordinates save, the screen shall show "Location not saved — the API needs updating." and shall not open the route (protects against a UI deployed before the API).
- **LOC-19** Any other API error shall be shown as text under the button.

### 7.4 Location follows address edits (address detail)

- **LOC-20** Saving an edited address whose street, city, state or zip changed shall look up the new position (E2) before the update and send it in the **same** `PUT` as the address fields. Changing only Address Line 2 shall not trigger a lookup.
- **LOC-21** If the lookup fails and the listing **had** a location, the same `PUT` shall send `latitude: 0, longitude: 0` (clearing the now-wrong position) and the screen shall show: "Couldn't find the new address on the map, so the old location was removed. Use “Locate & route” to try again or place it on the map."
- **LOC-22** If the lookup fails and the listing had no location, no coordinate fields shall be sent.
- **LOC-23** The save control shall be disabled while saving. Address validation messages (street required, state 2 letters, zip 5 digits or ZIP+4) are shown before any request.
- **LOC-24** `PUT` returning `modifiedCount: 0` shall show "Address not saved — the API needs updating."

### 7.5 Where locations are used

Map View and Route View plot only listings that have a location. Route View lists a ✅/❌ per listing for this; Route View shall not call the API to fix it (no locate action there yet, §10). "Find nearby" uses `GET /addressList/:id/nearby`, which only considers active listings in the same masjid that have a location. Admins see the raw latitude/longitude on the address detail screen **[Doc]**.

### 7.6 Tests

`geocode.test.js` (lookup rules and failures), `AddAddressGeocode.test.js`, `AddressDetailLocation.test.js` (locate, not-found choices, pin save, API-not-updated, edits that move/clear/leave the location). **Not covered by automated tests:** the real `PinPicker` map (Jest cannot load `react-leaflet`, an ES-module-only package; it is replaced by a stand-in), the real Mapbox/Nominatim responses, and the API change (the API repo has no tests).

**Sources:** `src/Components/AddressAutocompleteInput.js`, `AddAddress.js`, `AddressDetail.js`, `PinPicker.js`, `src/mapbox.js`, `src/geocode.js`.

## 9. Quality, testing and operations

- Unit tests: Jest + React Testing Library (`npm test`); end-to-end: Playwright (`npm run test:e2e`, needs a running UI and API plus `TEST_MASJID_PIN`).
- Known suite-level failure: `src/App.test.js` cannot run because Jest cannot parse `react-leaflet` (ES-module-only); it fails independently of the features above **[Open]**.
- Dates shall be formatted with `formatDate()` (`src/utils.js`), never `toLocaleDateString()`, because MongoDB UTC dates otherwise shift by a day.
- ESLint errors are bugs to fix at the root cause. A `feat` commit needs a functional-manual change staged (project hook).
- Docs that must be kept in step: the functional manuals (user-visible behavior), `docs/page-flow.md` and `docs/login_flow.md` (navigation/auth), `README.md` and `AGENTS.md` (Landing state/caching), `docs/changelog.md` (on release/push).

## 10. Open questions and known gaps

| # | Item | Why it matters |
|---|---|---|
| 1 | **Mapbox storage terms.** Suggestions use temporary geocoding results, while the chosen address text is saved in the database. Mapbox's terms restrict storing temporary results; `permanent=true` is the paid alternative. | Possible terms breach — decide between permanent geocoding, dropping Mapbox, or accepting the risk after reading the current terms |
| 2 | **No Nominatim cache or throttle in the UI.** Fine for one lookup per user action; a bulk run would break the 1 request/second rule. | Needed before any backfill |
| 3 | **Bulk backfill of existing listings** (those with `0`/`0`) is not built. The API change is already in place; it needs a throttled admin tool and a list of failures. | Without it, each listing is fixed one by one through Locate & route |
| 4 | **Match quality is unchecked.** The first Nominatim hit is accepted; there is no check that it is near the masjid or that it is street-level. | A wrong pin sends volunteers to the wrong place |
| 5 | **Failed lookup on edit clears the old location** (`LOC-21`). This was a design choice to avoid stale pins. | Confirm with the product owner |
| 6 | **Locate action missing in Route View**, which shows ❌ for listings without a location but offers no fix. | Natural next step |
| 7 | **Public demo services** (OSRM, OSM tiles, Nominatim) have no uptime guarantee and fair-use limits. | Reliability and policy risk as usage grows |
| 8 | **`PinPicker` and the API change have no automated tests**; `App.test.js` does not run. | Test debt |
| 9 | **Docs drift** (§2) between `AGENTS.md` and `App.js`. | Misleading guidance |
| 10 | **`allowUpdateExisting`** path in Add Address is built but switched off. | Dead/unreleased behavior |
| 11 | Sections marked **TODO** (§2) are not yet reverse-engineered. | Spec incomplete |
| 12 | **Masjid editor uses Nominatim for search-as-you-type** (`MasjidDetail.js`), against the public server's policy. Options: switch it to the Mapbox suggestions used on Add Address, or remove the typing suggestions and keep a single lookup on demand. | Risk of the site being blocked by Nominatim, which would also break the listing lookups in §7 |
| 13 | The masjid editor and the listing form use **different suggestion providers** (Nominatim vs Mapbox) with different result shapes. | Inconsistent behavior and two sets of rules to maintain |
